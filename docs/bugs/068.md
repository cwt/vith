# `import vith.__main__` starts the editor (unguarded `run()`)

**Category:** wrong logic / import side-effect · **Area:** `vith/__main__.py`, `vith/entry_points/run_vith.py` · **Found at:** deep review, hg rev 87de3a3 (2026-11-08) · **Re-validated:** 2026-11-08 at hg rev 251 (tip; code identical to the audit revision)

## Summary

```python
# vith/__main__.py
from .entry_points.run_vith import run
run()   # top level, no guard
```

`python -m vith` works because the module runs as `__main__`, but *any* import of `vith.__main__` (tooling, docs, a test that imports the submodule for `run` discovery) executes `docopt` + `Editor()` + `application.run()`.

## Evidence

* [`vith/__main__.py:1-7`](../../vith/__main__.py)[^src-main] — exactly seven lines: docstring, then the import, then a bare `run()` (`:7`) with no `if __name__ == "__main__"` guard. The side-effect chain is verified end-to-end: `run_vith.py:28` (`docopt`), `:36` (`Editor()`), `:52` (`editor.run()` → `editor.py:385` `self.application.run(...)`).
* [`vith/entry_points/run_vith.py:55-56`](../../vith/entry_points/run_vith.py) — the *other* entry point guards correctly with `if __name__ == '__main__'`.

## Impact

Surprising side-effect on import; breaks import-time tools; `python -m vith` still needs the guard form (`if __name__ == "__main__": run()`).

## Fix direction

Add the guard; keep `python -m vith` behavior (module executed as `__main__` still triggers).
