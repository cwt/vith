# `DocumentLexer` joins lines to EOF per edit and `_sanitize_and_invalidate_sara_am` inflates sparse `Screen.data_buffer` rows/columns

**Category:** unoptimized algorithm · **Area:** `vith/lexer.py`, `vith/thai.py`, `vith/layout.py` · **Found at:** deep review, hg rev 191 (2026-11-07)

## Summary

Three secondary hot paths perform avoidable allocations:

1. **`'\n'.join(document.lines[start_lineno:])[column:]` in `DocumentLexer.lex_document`** ([`vith/lexer.py:122`](../../vith/lexer.py)[^src-lex]):
   Although [`030`](030.md) noted the to-EOF join in `DocumentLexer`, `vith/lexer.py:122` still executes:
   ```python
   text = '\n'.join(document.lines[start_lineno:])[column:]
   ```
   When editing near the top of a 10,000-line file, `start_lineno` is near 0, so every edit slices `document.lines`, joins all lines to EOF into a new string, and slices `[column:]` again. Because `document.text` already holds the joined buffer text, slicing `document.text[document.translate_row_col_to_index(start_lineno, column):]` avoids the `list` slice and `'\n'.join(...)` completely.
2. **Sparse `Screen.data_buffer` (`defaultdict`) inflation in `_sanitize_and_invalidate_sara_am`** ([`vith/thai.py:953-995`](../../vith/thai.py)[^src-thai]):
   `prompt_toolkit.layout.screen.Screen.data_buffer` is a nested `defaultdict(lambda: defaultdict(lambda: default_char))`. In `_sanitize_and_invalidate_sara_am`:
   * Line 976 computes `all_ys = set(new_db.keys()) | set(prev_db.keys())` and line 978 indexes `new_row = new_db[y]`, creating empty row dicts in `new_db` for rows `y` that only existed in `prev_db`.
   * Lines 988–990 loop `for x in range(1, max_x): prev_cell = prev_row[x]; cur_cell = new_row[x]`, which populates `default_char` entries in both `prev_row` and `new_row` for every unpopulated column `x < max_x` (inflating sparse rows before upstream `_output_screen_diff` iterates over `row.keys()`).
3. **Empty regex iteration in `BufferListOverlay.highlight_location`** ([`vith/layout.py:219`](../../vith/layout.py)[^src-lay]):
   When the user types `:b ` with an empty search string (`search_string == ''`), `highlight_location` runs `re.finditer(re.escape(''), location)`, matching at every character boundary (`len(location) + 1` zero-length matches) instead of returning `[('', location)]` in $O(1)$.

## Evidence

* [`vith/lexer.py:121-125`](../../vith/lexer.py)[^src-lex]:

  ```
* [`vith/thai.py:976-991`](../../vith/thai.py)[^src-thai]:

  all_ys = set(new_db.keys()) | set(prev_db.keys())
  for y in all_ys:
      new_row = new_db[y]
      prev_row = prev_db.get(y)
      ...
      for x in range(1, max_x):
          prev_cell = prev_row[x]
          cur_cell = new_row[x]
  ```

## Impact

* Extra string allocations on edits near the top of large files (`DocumentLexer`).
* Unnecessary population of sparse `Screen.data_buffer` cells when `_THAI_GATE.value` is `True` (`_sanitize_and_invalidate_sara_am`).

## Fix direction

1. In `vith/lexer.py:122`, compute `start_index = document.translate_row_col_to_index(start_lineno, column)` and slice `text = document.text[start_index:]`.
2. In `vith/thai.py:976-991`, use `new_row = new_db.get(y)` and iterate over `for x in set(new_row.keys()) | set(prev_row.keys()):` (with `.get(x)`) instead of `range(1, max_x)` and `row[x]`.
3. In `vith/layout.py:219`, return `[('', location)]` immediately when `not search_string`.
