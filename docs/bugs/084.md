# Visual-block `d` cuts wider than the highlight (operator cursor decrement)

**Category:** wrong corner derivation (stem: 076/077/079) · **Area:** `vith/thai.py` (`_thai_selection_ranges` BLOCK branch) · **Found at:** stem audit 2026-11-08 · **Fixed at:** hg rev 271

## Summary

prompt_toolkit `TextObject.cut` (vi.py:146-156) turns a block operator into
`Document(text, cursor_position = cursor - 1, ...)`. When the pre-cut cursor
column ≥ 1 and the *previous* codepoint is that cluster's own combining mark,
the decremented cursor sits **mid-cluster**; `_thai_selection_ranges` then
re-derives the corner ordinals from it and the mark's cluster base pulls the
low/high corner one cell off — cut ≠ highlighted rectangle.

Repro (post-077 code, real keys): `<C-v> j` with cursor on `ส` of `สีส` —
highlight ranges `[(3, 5), (9, 10)]` (cells ordinal 1..1) but the cut took
`ที่ดิ`/`สีส` (ordinal 0..1).

## Fix

`_thai_selection_ranges` compensates the **cursor-side** corner only: when
`line[cursor_col]` is a combining mark, `cursor_pos += 1` (the operator's
decrement), and then all corner ordinals re-derive identically to the
highlight state.

E2E test: `tests/test_thai.py::test_block_d_aligned_with_highlight` —
`l` `C-v` `j` `d` on `ที่ดิน\nสีส\nxyz\n` → clipboard == exactly the
highlighted cells (`ดิ` / `ส`) and the post-text is `ที่น\nสี\nxyz\n`.

*Siblings documented:* (a) block `d` at **column 0 of the last row** loses that
row entirely (upstream ptk behavior, identical for ASCII — our patches cannot
resurrect a row prompt_toolkit never yields) — accepted as upstream parity;
(b) a textobject-decrement port from the same file (`TextObject.cut`)
interacts only via the compensated corner (verified in the same probe set).
