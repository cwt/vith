# SARA-AM renderer sanitizer scans the full screen on every frame, even for ASCII-only files

**Category:** performance · **Area:** `vith/thai.py` (renderer patch) · **Found at:** deep review, hg rev 164 (2026-11-06)

## Summary

`_sanitize_and_invalidate_sara_am` iterates every row and every column of both
the new and the previous screen on **every render frame**, regardless of
whether the document contains any Thai/Lao character at all.

## Evidence

* The wrapper installed on `prompt_toolkit.renderer._output_screen_diff`
  ([`vith/thai.py:852-859`](../../vith/thai.py)) calls the sanitizer before
  every diff loop; the diff loop of prompt_toolkit itself is the only other
  already-full-grid scan per frame.
* The sanitizer ([`vith/thai.py:776-824`](../../vith/thai.py)) builds a row-index
  union set, does `list(new_row.items())` per row, then a `range(1, max_x)`
  loop with `_cell_has_sara_am` (`vith/thai.py:766-773`) per cell —
  O(rows × cols) pure-Python work.
* Measured (Python 3.15.2, prompt_toolkit 3.0.53): 50×200 screen
  (10,000 cells) = **1.27 ms/frame with content containing Thai on one row**,
  and **still 1.27 ms/frame on a pure-ASCII screen** — i.e. every file without
  a single Thai character pays the toll.
* Context: the P1 lexer budget after optimization is ~1.17 ms for the visible
  window (see [`speed_latency_plan.md §1.2`](../speed_latency_plan.md)), so
  the sanitizer roughly doubles the per-keystroke render cost on large
  full-screen renders.

## Impact

Per-keystroke render latency is dominated by a scan that can be avoided for
ASCII-only documents entirely, and reduced for Thai documents via
short-circuiting.

## Fix direction

Gate the whole pass on a cheap per-text-version flag ("document contains any
Thai/Lao codepoint"), e.g. cache `document.text.isascii() == True → skip` or
any Thai codepoint check computed once per text change. Optionally
short-circuit per row before entering the x-loop.
