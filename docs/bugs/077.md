# Visual block over Thai lines is not rectangular (block columns count combining marks)

**Category:** wrong logic / Vim semantics · **Area:** `vith/thai.py` (`_thai_selection_range_at_line`, BLOCK selection) · **Found at:** user bug report 2026-11-08, hg rev 267 · **Fixed at:** hg rev 268

## Summary

prompt_toolkit computes the visual-block rectangle from **codepoint columns**
(`Document.selection_range_at_line`, BLOCK branch: `col1/col2 = translate_index_to_position(...)`).
For Thai/Lao text every upper/lower vowel and tone mark (`GC=Mn`) is its own codepoint
column, although it overprints the preceding base on screen (zero width). Rows with
different numbers of leading combining marks therefore disagree on where “column k” is:

* the highlight starts/ends **mid-cluster** (e.g. on a `ั` mark) instead of whole cells, and
* rows before/after clusters of different widths do not line up — the block is not a
  rectangle on the terminal, exactly like Vim until TCC-aware block selection.

In Vim, a visual block over Thai rows covers **visual columns**; every cluster
(`base + marks*`) is exactly one cell, so the rectangle is defined on cell ordinals.

## Evidence

* [`vith/thai.py` — `_thai_selection_range_at_line` pre-fix](../../vith/thai.py): only handled the char-selection upper bound (`end - 1` mark snap, docs/bugs/076); the BLOCK path fell through untouched.
* prompt_toolkit `document.py:954-1005` — BLOCK branch selects per-row codepoint columns (`col1, col2 = sorted(translate(from_), translate(to_))`, per-row `translate_row_col_to_index(l, min(line_length, to_column))`).
* User report: “visual block is still counting upper/lower vowels so visual block on multiple Thai lines is not rectangle.”

## Fix

`_thai_selection_range_at_line` now special-cases `SelectionType.BLOCK`:

1. The selection corners (sorted absolute cursor/origin positions) are converted to **visual columns** by counting cell-cluster starts on their corner rows (`_cell_ordinal`).
2. Per row, the span is mapped back to codepoints through the row's `cell_starts` (`_start_of_cell_ordinal`): the start is the row's cluster containing the lower visual column, the end is the start of the cluster after the upper visual column.
3. `max(existing, mapped_end)` preserves prompt_toolkit's own `len(line) + 1` EOL column so its empty-line space-marker behavior survives.
4. Rows with fewer cells than the rect's visual range highlight only their EOL space (like Vim's empty rect edge).
5. ASCII rows keep `ordinal == codepoint` identity, so the vanilla rectangle is byte-for-byte preserved (test-pinned).

Char (`v`) selections keep the 076 semantics (only the *last selected cell* extends over its own marks — Vim `v` does not snap the left edge).

## Tests

* `tests/test_thai.py::test_block_selection_rectangles_align_on_cells` — corners on cluster ordinal 2 across rows `ที่ดิน / ปั้ / กำแพง` yield `(5, 6)`, `(3, 4)` (EOL space only — no cell at that visual column), `(2, 6)`; LINES selections pass through.
* `tests/test_thai.py::test_block_selection_ascii_rectangle_matches_vanilla` — ASCII block equals prompt_toolkit's own columns per row.
* Real-render BLOCK sweep over a 5-row Thai document (all corner/cursor pairs through `HighlightSelectionProcessor`) — zero crashes.
