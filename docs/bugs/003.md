# Tab completion on `.py` buffers raises uncaught `ImportError` when jedi is not installed

**Category:** robustness · **Area:** `vith/completion.py` · **Found at:** deep review, hg rev 164 (2026-11-06)

## Summary

jedi is an **optional** dependency (not present in `install_requires`), but
Python-file completion is selected whenever the `.py` extension and
`editor.enable_jedi` (default `True`) agree — and `_get_jedi_script_from_document`
performs a bare inline `import jedi` outside any exception guard.

## Evidence

* Selection: [`vith/completion.py:94-97`](../../vith/completion.py)
  (`location.endswith('.py') and editor.enable_jedi` → `_PythonCompleter`).
* Default-on: [`vith/editor.py:64`](../../vith/editor.py)
  (`self.enable_jedi = True`).
* jedi absent from install_requires: [`setup.py:19-25`](../../setup.py).
* The import happens per call with **no** try/except:
  [`vith/completion.py:152-154`](../../vith/completion.py) — the runtime errors
  of `get_completions` (TypeError/UnicodeDecodeError/…) are guarded
  (`completion.py:123-146`), but the missing-module `ImportError` from the
  in-line import propagates out of the generator on the first completion.

## Impact

On any environment where jedi is not installed (a supported configuration per
`setup.py`), pressing Tab inside a `.py` file crashes the completion path with
an unhandled `ImportError` — prompt_toolkit surfaces the exception and takes
down the session. The test suite never hits this: it uses
`pytest.importorskip('jedi')` ([`tests/test_completion.py:92-93`](../../tests/test_completion.py)).

## Fix direction

Wrap the jedi import in `try/except ImportError` and fall back to the words
completer for the rest of the session (optionally with a one-time status
message), or gate completer selection on jedi availability instead of the
flag alone. Add a test that forces the import to fail.
