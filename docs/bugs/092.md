# Visual block over lines with SARA AM overshoots (`max` bleeds codepoint columns)

**Category:** coordinate-space confusion / over-extension (stem: 077/079/084) · **Area:** `vith/thai.py` (`_thai_selection_range_at_line` and `_thai_selection_ranges` BLOCK branch) · **Found at:** user report with `Screenshot_2026-11-09_10-30-50.png` 2026-11-09 · **Fixed at:** working tree

## Summary

In `_thai_selection_range_at_line` and `_thai_selection_ranges`, the visual block end was computed using:
```python
end = max(end, _start_of_cell_ordinal(line, v_high + 1))
to = max(to, end_abs)
```
The intention (documented in finding [077](077.md)) was to preserve prompt_toolkit's `len(line) + 1` EOL space column on short lines so empty-line/trailing space markers would render.

However, `end` and `to` from vanilla prompt_toolkit are **codepoint columns** derived from `to_column = col2 + 1`. When another row has multiple combining marks (such as row 4 `"ฉันจะฝันถึงเธอ"`, where `'ฉั'` has 2 codepoints, placing the cursor on `'น'` at codepoint 2 and `to_column = 3`), prompt_toolkit returns `end = 3` for every row.

On rows with fewer combining marks—specifically Thai lines containing `SARA AM` (`U+0E33`, `GC=Lo`, width 1, e.g. `"ทำอะไรอยู่"` where `'ท'` is codepoint 0, `'ำ'` is codepoint 1, and `'อ'` is codepoint 2)—the visual cell boundary for column 1 ends at codepoint index 2 (`'ทำ'`). But `max(3, 2)` evaluated to 3, forcing the highlight to bleed onto `'อ'` (`'ทำอ'`), making that row 3 cells wide instead of 2.

## Evidence

* `Screenshot_2026-11-09_10-30-50.png` shows lines:
  1. `สวัสดีครับ` — highlight on `สวั` (2 cells)
  2. `ทำอะไรอยู่` — highlight on `ทำอ` (3 cells, protruding rightward)
  3. `ปีใหม่นี้ดีไหม` — highlight on `ปีใ` (2 cells)
  4. `ฉันจะฝันถึงเธอ` — highlight on `ฉัน` (2 cells)
* [`vith/thai.py`](../../vith/thai.py): `end = max(end, _start_of_cell_ordinal(line, v_high + 1))` and `to = max(to, end_abs)` unconditionally preserved prompt_toolkit's codepoint column even within the line body.
* `tests/test_thai.py:1045`: `assert row2 == (2, 6)` in finding 077's test previously codified this blowout on `'กำแพง'` (selecting 4 cells for a 1-cell rect).

## Fix

1. In `_thai_selection_range_at_line`, only retain prompt_toolkit's `end` if the block actually extends to/past EOL (`cell_end >= len(line)`) AND prompt_toolkit flagged an EOL space (`end > len(line)`). Otherwise, clamp `end` strictly to `cell_end = _start_of_cell_ordinal(line, v_high + 1)`.
2. In `_thai_selection_ranges`, set `to = end_abs` directly since in-document selection slices do not include the post-EOL virtual space.
3. Updated `tests/test_thai.py` assertion for row 2 to `(2, 3)` (1 cell wide) and added regression test `test_block_selection_with_sara_am` covering the exact 4-line reproduction.
