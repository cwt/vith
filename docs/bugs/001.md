# Thai/Lao word motions re-segment the entire document on every motion key

**Category:** performance · **Area:** `vith/thai.py` · **Found at:** deep review, hg rev 164 (2026-11-06)

## Summary

Every Thai/Lao word-level motion or text object re-scans the **complete document
text** from scratch and rebuilds word spans, including a per-chunk `libthai`
ctypes round-trip (`th_brk_wc_find_breaks`). Nothing is cached between presses,
and multi-count presses (`3w`, `5e`) pay the full cost again.

## Evidence

* Every motion rebuilds spans via `_iter_word_spans(doc.text)`:
  [`vith/thai.py:485-546`](../../vith/thai.py) (`find_next/previous_word_beginning/ending`),
  `616-662` (`find_boundaries_of_current_word`). Also used by vi text objects
  (`iw`/`aw`/`*`/`#`) through the patched `Document` methods.
* `_iter_word_spans` (`vith/thai.py:462-482`) regex-scans the whole text and
  calls `find_thai_word_breaks` (`vith/thai.py:428-453`) separately for **each
  Thai chunk**; `find_breaks` (`vith/thai.py:297-317`) builds a
  `(c_uint32 * n)` codepoint array plus `c_int` buffers and crosses into
  `libthai` via ctypes on every call.
* Measured (Python 3.15.2, libthai active, Linux x86_64):
  `_iter_word_spans` over a 2.4 MB / 3,001-line Thai document = **644 ms**
  (504,000 spans; ~36,000 chunks at ~16 µs each); one
  `find_next_word_beginning` (= one `w` press) = **~640 ms**;
  10 `w` presses = **6.4 s**.
* The ASCII fast path delegates to the original `Document` method and stays
  fast; the pathology only affects documents containing Thai/Lao text.
* Existing tests use tiny documents only
  ([`tests/test_thai.py:415-497`](../../tests/test_thai.py)), which masks the cost.

## Impact

Motion latency scales linearly with file size plus heavy per-chunk ctypes
overhead — `w`, `b`, `e`, `W`, `B`, `E`, `dw`, `cw`, `iw`, `aw`, `*`, `#` all
become seconds-long on large Thai files. This contradicts the performance
intent documented in [`thai_support_plan.md §3.4`](../thai_support_plan.md)
(sub-µs per-keypress scanner goal).

## Fix direction

Memoize the span list per text version (same strategy as the P3 completion
cache: key on `(text-version, …)` stored on `EditorBuffer` or module state), or
restrict scanning to the paragraph/visible region with the full scan only as
a fallback. Incremental reuse of unchanged lines removes the per-chunk ctypes
cost from steady-state movement.
