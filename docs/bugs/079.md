# Visual-block `I`/`A` anchors split Thai clusters

**Category:** wrong logic / Vim semantics (extrapolated from 077) · **Area:** `vith/thai.py` (`_thai_selection_ranges`, BLOCK) · **Found at:** extrapolation audit 2026-11-08, hg rev 268 · **Fixed at:** hg rev 269

## Summary

vi.py's visual-block `I`/`A` (multi-cursor insert; `vi.py` iterates
`buff.document.selection_ranges()` and stops at either edge per row) is the
**absolute-space** consumer of the selection stack — while the 077 fix covered
only the rendering consumer (`selection_range_at_line`, line-relative). The
Thai wrapper `_thai_selection_ranges` extended the *end* over trailing marks but
left the *start* untouched, so with corners on a combining mark:

* repro (pre-fix): block with corners at cp col 1 → ranges `(1, 3)`, `(8, 10)` —
  anchors on `ี` and `ั` (mark columns). Typing at an anchor produced
  `ทีX…`/`ปX…` — the cluster is split, the mark re-attaches to the inserted text.
* Vim inserts at cell boundaries: before `[ที่]` / `[ปั้]`.

## Fix

`_thai_selection_ranges` now computes the block rectangle on **cell-cluster
ordinals** from the sorted corner positions (the same model as 077: corners →
`(v_low, v_high)` via `_cell_ordinal` on the corner rows) and per yielded row
maps back to codepoints through `cell_starts`:

* `from_` = start of the cell containing `v_low` (the `I` anchor precedes whole cells);
* `to` = `max(ptk's own, start of the cell after `v_high`)` (the `A` anchor follows whole cells).
* CHAR/LINES selections keep the existing trailing-mark extension; ASCII blocks
  are prompt_toolkit's own ranges (identity asserted by test).

## Tests
* `tests/test_thai.py::test_block_selection_ranges_align_on_cells` — corners at cp 1/8 → ranges `(0, 3)`, `(7, 10)` (whole `[ที่]`/`[ปั้]` cells).
* `tests/test_thai.py::test_block_selection_ranges_ascii_matches_vanilla` — ASCII block == vanilla ranges.
* Full suite: 186 tests green (with 078 in the same commit).
