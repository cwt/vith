# CSV/TSV cells are interpreted as Rich markup

**Category:** live render / CSV · **Area:** `vith/render.py` · **Found at:** Round 11 deep correctness audit (2026-11-23, `v0.16.0` / rev 410) · **Fix status:** fixed
> **Resolution note (2026-11-23):** Wrapped every CSV/TSV header and cell in `rich.text.Text` so markup-looking data is displayed literally.


## Summary

`_render_csv_table()` builds a Rich `Table` by passing the raw Python `str`
values from `csv.reader` directly to `table.add_column(col_name)` and
`table.add_row(*padded)`.[^src-render] Rich treats every `str` argument as
markup, so CSV cell text is not displayed faithfully:

* a cell containing `[/]` or `[/tag]` raises `rich.errors.MarkupError`;
* a cell such as `[bold]X` is rendered as styled `X` with the literal brackets
  removed — silent data corruption in a data-preview pane.

Because the worker classifies any generic `Exception` as `incomplete=True`
([171](171.md)), the first case freezes the preview on the previous good render
with a `• stale` title and no diagnostic, which is especially misleading for a
permanent content-dependent failure.

## Evidence

| Input (`filetype='csv'`) | Expected | Actual |
| :--- | :--- | :--- |
| `a,b\n[bold]X,[/]Y\n` | table showing literal `[bold]X` and `[/]Y` | `MarkupError: closing tag '[/]' at position 0 has nothing to close` |
| `a,b\n1,[notatag]v[/notatag]\n` | literal `[notatag]v[/notatag]` | table cell shows `v` (markup stripped) |
| `[bold]header,c\n1,2\n` | literal `[bold]header` header | header shows `header` |

Contradicts `docs/live_render.md` §5, which promises bounded, faithful
CSV/TSV table rendering via `rich.table.Table`.[^src-doc]

## Fix Direction

1. Wrap every header/cell string in `rich.text.Text(...)` (the canonical
   "display literally" type) before `add_column`/`add_row`, or apply
   `rich.markup.escape()` to the raw strings. Keep the row cap and padding.
2. Add regression tests covering markup-looking cells (`[/]`, `[bold]X`) in
   both header and body positions for CSV and TSV, asserting exact cell text
   and no exception.
3. Separately, reclassify renderer-internal exceptions as non-transient errors
   so a permanent failure shows a diagnostic instead of a stale badge
   ([171](171.md)).
