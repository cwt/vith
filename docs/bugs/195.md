# VS16-promoted narrow emoji counted as one cell instead of two

**Category:** display-width model · **Area:** `vith/thai/clusters.py`, `vith/thai/classify.py`, `vith/cold_text.py`, `vith/thai/patches.py` · **Found at:** user field report (wide emoji drift vs. szn `variation-selector-always-wide`) · **Fix status:** fixed

## Summary

For the 213 base codepoints in `wcwidth`'s `VS16_NARROW_TO_WIDE` table, `get_cwidth(base) == 1` and `get_cwidth(base + U+FE0F) == 1` (because U+FE0F is `Mn`/zero-width), but `wcswidth(base + U+FE0F) == 2`. Terminals that widen emoji presentation (Kitty, Alacritty, and szn with `variation-selector-always-wide on`) render the pair as 2 cells, so vith under-measures by one column per occurrence. This skews `_line_visual_width`, `_cell_ordinal`/`_start_of_cell_ordinal`, `_cursor_vertical`, and visual-block rectangles.

## Evidence

```python
from vith.thai.clusters import _line_visual_width
_line_visual_width('❤️')  # 1 by default
# wcswidth('❤️') == 2
```

All 213 narrow bases in `wcwidth.table_vs16.VS16_NARROW_TO_WIDE['9.0.0']` reproduce the mismatch.

## Resolution

Added an opt-in `variation_selector_always_wide` option (default off), exposed through `Editor`, `:set variation_selector_always_wide`, and TOML config. When enabled, `_compute_cell_columns` counts a narrow base followed by U+FE0F as 2 cells. Module-level flags `variation_selector_always_wide` / `VARIATION_SELECTOR_ALWAYS_WIDE` in `vith.thai.clusters` (and `vith.thai`) control the same behavior for direct callers/tests.
