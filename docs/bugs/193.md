# Thai/Lao upper/lower vowels and tone marks dropped on Windows ConPTY input

**Category:** Thai/Lao / Windows input · **Area:** `vith/thai/patches.py` (`prompt_toolkit.input.win32`) · **Found at:** user field report on Windows 11 (`10.0.26300.0`) + Alacritty (`0.18.0-dev`) (`v0.16.1` / rev 435) · **Fix status:** fixed

> **Resolution note (2026-11-23):** Added `_install_win32_input_patch` in `vith/thai/patches.py` (installed by `install_prompt_toolkit_thai_patches()` on `sys.platform == "win32"`, with signature verification and rollback tracking). Both `prompt_toolkit.input.win32.Vt100ConsoleInputReader._get_keys` and `ConsoleInputReader._get_keys` now accept synthesized Alt+Numpad `VK_MENU` (`0x12`) key-up Unicode deliveries (`KeyDown == 0`, `VirtualKeyCode == 0x12`, `uChar.UnicodeChar != "\x00"`) alongside normal `KeyDown` records, using a shared `_iter_win32_events` helper and Python 3.10 `match`/`case` dispatch. Verified in a live Windows ConPTY session (87/87 Thai codepoints preserved on both typing and bracketed paste) and pinned with unit tests in `tests/test_thai.py`.

## Summary

On Windows terminals backed by ConPTY (`C:\Windows\system32\conhost.exe`, including Alacritty and Windows Terminal), typing or pasting Thai text into `vith` caused all upper/lower vowels and tone marks to vanish (`"ที่ดิน ผู้ใหญ่ น้ำ"` became `"ทดน ผใหญ นำ"`), even though plain Alacritty (`pwsh` / `PSReadLine`) and `vith`'s output path displayed Thai combining marks properly.[^src-patches]

The root cause is a two-layer interaction between Windows ConPTY and `prompt_toolkit`:

1. **ConPTY (`conhost.exe` `CharToKeyEvents`) synthesizes `VK_MENU` key-up events for non-`C3_ALPHA` characters.** When translating UTF-8 input from the terminal pipe into Win32 `KEY_EVENT_RECORD`s, `conhost.exe` first calls `VkKeyScanW(wch)`. Because the headless `conhost.exe` process runs with the default US English keyboard layout (`0x4090409`), `VkKeyScanW` returns `-1` for all Thai/Lao characters. `conhost.exe` then checks `GetStringTypeW(CT_CTYPE3, &wch, 1, &type) & C3_ALPHA`:
   * The **55** Thai consonants and spacing vowels (`ก–ฮ`, `ะ`, `า`, `ำ`, `เ`, `แ`, `โ`, `ใ`, `ไ`, `ๅ`) have `C3_ALPHA` set and are emitted as standard `KeyDown=1` events (`VK=0`, `UnicodeChar=ch`).
   * The remaining **32** Thai characters — **all 16 combining marks** (`ั` `U+0E31`, `ิ–ฺ` `U+0E34..U+0E3A`, `็–๎` `U+0E47..U+0E4E`) plus `ฯ`, `ๆ`, `฿`, `๏`, Thai digits `๐–๙`, `๚`, `๛` (and 43 Lao codepoints including all 17 Lao combining marks) — lack `C3_ALPHA`. For these, `conhost.exe` falls back to `SynthesizeNumpadEvents`, emitting a synthetic Alt+Numpad sequence (`VK_MENU` down, numpad digits, then **`VK_MENU` up (`KeyDown=0`, `VirtualKeyCode=0x12`)** carrying the actual `uChar.UnicodeChar`). This happens under both `chcp 437` and `chcp 65001` and affects bracketed paste as well.
2. **`prompt_toolkit.input.win32` discards all `KeyDown == False` records.** Both `Vt100ConsoleInputReader._get_keys` (active under ConPTY) and `ConsoleInputReader._get_keys` filter strictly on `isinstance(ev, KEY_EVENT_RECORD) and ev.KeyDown`, dropping every `VK_MENU` key-up delivery. By contrast, `ReadConsoleW` and `PSReadLine` handle Windows Console's Alt+Numpad `VK_MENU` key-up Unicode convention natively.

## Evidence

Live `CreatePseudoConsole` (`conhost.exe`, Windows `10.0.26300.0`, `prompt_toolkit 3.0.53`) probes:

* `GetStringTypeW(CT_CTYPE3) & C3_ALPHA` matched the observed `KeyDown=1` vs `KeyDown=0, VK_MENU` split across all **87/87** Thai codepoints (`0` mismatches).
* Raw `ReadConsoleInputW` sequence emitted by ConPTY for `'ี'` (`U+0E35`):
  ```text
  KeyDown=1  VK=18 (VK_MENU)   uChar='\x00'  ControlKeyState=0x2
  KeyDown=1  VK=102 (NUMPAD6)  uChar='\x00'  ControlKeyState=0x2
  KeyDown=0  VK=102 (NUMPAD6)  uChar='\x00'  ControlKeyState=0x2
  KeyDown=1  VK=99 (NUMPAD3)   uChar='\x00'  ControlKeyState=0x2
  KeyDown=0  VK=99 (NUMPAD3)   uChar='\x00'  ControlKeyState=0x2
  KeyDown=0  VK=18 (VK_MENU)   uChar='ี'     ControlKeyState=0x0
  ```
* End-to-end `vith.exe` inside Windows ConPTY (`sample = "ที่ดิน ผู้ใหญ่ น้ำ กล้ำ ปู กุ้ง ตี๋ ฯๆ฿๑๒๓"`):

| Path | Before fix | After fix |
| :--- | :--- | :--- |
| Typing in Insert mode | `'ทดน ผใหญ นำ'` (all 32 non-`C3_ALPHA` chars dropped) | `'ที่ดิน ผู้ใหญ่ น้ำ กล้ำ ปู กุ้ง ตี๋ ฯๆ฿๑๒๓'` (87/87 Thai codepoints preserved) |
| Bracketed paste (`\x1b[200~…\x1b[201~`) | `'ทดน ผใหญ นำ กลำ'` | `'ที่ดิน ผู้ใหญ่ น้ำ กล้ำ ปู กุ้ง ตี๋ ฯๆ฿๑๒๓'` |
| `Alt+x` / Arrow / `Ctrl+C` | Unaffected (`VK != 0x12` on key-up) | Unaffected (`VK != 0x12` on key-up) |
| Opening saved UTF-8 Thai file (output) | Full clusters emitted through ConPTY | Full clusters emitted through ConPTY |

## Fix Direction

1. On `sys.platform == "win32"`, patch `Vt100ConsoleInputReader._get_keys` and `ConsoleInputReader._get_keys` inside `install_prompt_toolkit_thai_patches()` (with signature verification and rollback registration) to also yield characters from `KEY_EVENT_RECORD`s where `not ev.KeyDown and ev.VirtualKeyCode == 0x12 and ev.uChar.UnicodeChar != "\x00"`.
2. In `ConsoleInputReader._get_keys`, construct `KeyPress` directly for `VK_MENU` key-up events (mapping control bytes via `self.mappings`) instead of calling `_event_to_key_presses`, which asserts `ev.KeyDown`.
3. Add regression tests in `tests/test_thai.py` covering both readers and startup self-test rollback.[^src-tests]
