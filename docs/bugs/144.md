# `:retab` rewrites leading spaces without `!` when `noexpandtab`

**Category:** wrong logic / whitespace conversion · **Area:** `vith/commands/commands.py` (`_retab_line`, `retab_lines`) · **Found at:** Round 8 full re-audit, 2026-11-19, hg rev 358 (`ff583fcf26ba`) · **Fix status:** open

## Summary

`_retab_line()` branches on:

```python
elif start_col == 0 or has_tab or (force and len(run) >= 2):
    out.append(_encode_retab_ws(start_col, col, new_ts, False))
```

([`vith/commands/commands.py:2729-2732`](../../vith/commands/commands.py#L2729-L2732)).

When `expand_tab` is false, `start_col == 0` causes **every leading
whitespace run**, including a pure-space indent, to be converted to tabs even
when `force` (`:retab!`) is absent. Vim's `:retab` without `!` only replaces
sequences of whitespace that contain a `<Tab>`; it leaves space-only indents
alone. (`:retab!` is the form that also converts spaces.)

## Evidence

Probe: `:set noexpandtab`, then a line with eight leading spaces:

```text
input  '        eight'
:retab -> '\teight'
```

Vim (same file, `set noexpandtab` then `retab`) leaves the eight spaces
unchanged. `:retab!` converts it in both files.

The implementation test at
[`tests/test_range_commands.py:319-323`](../../tests/test_range_commands.py#L319-L323)
explicitly asserts the leading-indent conversion, so the suite locks the
deviation in instead of comparing it with Vim; there is no space-only
`noexpandtab` case that documents the intended Vim rule.

## Impact

* A plain `:retab` can silently change indentation style in Makefiles or files
  that intentionally use spaces without expandtab.
* `:retab N` (changing tabstop) has the same side effect on every leading
  space-only indent.

## Fix direction

1. In noexpandtab mode, require `has_tab` (or `force`) before re-encoding; do
   not special-case `start_col == 0`.
2. Keep the leading-indent behavior for `:retab!` only.
3. Add tests for space-only, tab+space, and mixed indents with both
   `expandtab` and `noexpandtab`, with and without `!`.
