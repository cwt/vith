# Thai cluster & word-motion hot spots (`clusters.py` and `words.py`)

**Category:** performance / algorithms · **Area:** `vith/thai/clusters.py`, `vith/thai/words.py` · **Found at:** Round 10 deep performance audit (2026-11-22, `v0.15.1` / rev 392) · **Fix status:** open

## Summary

Four localized algorithmic inefficiencies remain in the Thai cluster and word-motion modules:

1. **`cell_stops` and `_compute_cell_columns` (`vith/thai/clusters.py:78-152`):**[^src-clusters]
   - `cell_stops` calls `next_cell_offset(line, col, 1)` in a per-character loop even when `line.isascii()` (which is simply `list(range(len(line) + 1))`).
   - `_compute_cell_columns` calls `cell_stops(line)` and then allocates a string slice `line[start:end]` and a generator expression `sum(get_cwidth(char) for char in line[start:end])` for **every single cluster** — including pure-ASCII lines that contain a tab (`\t`).
2. **Word-motion tuple copying & linear scan (`vith/thai/words.py:332-543`):**[^src-words]
   - `_iter_word_span_rows` copies the entire cached `_word_spans_for_line` tuple into a new `list` (and reverses it for `b`/`ge`), then linearly scans from column 0 on the cursor line.
   - `find_next_word_ending` calls `prev_cell_offset(line, end, 1)` on **every word before the cursor** on the cursor line before discarding it.
   - `find_boundaries_of_current_word` linearly scans all spans on the line instead of binary-searching (`bisect`).
3. **Missing ASCII fast path in `_cluster_aligned_spans` & eager `r1_end` in `find_thai_cluster_end` (`vith/thai/words.py:167, 255-285`):**[^src-words]
   - `_cluster_aligned_spans` inspects `is_combining_char` on every span boundary even when `line.isascii()` is `True` (e.g., ASCII lines inside a mixed-script document).
   - `find_thai_cluster_end` unconditionally computes `r1_end = next_cell_offset(line, after_base, 1)` before checking `ord(line[after_base]) == 0x0E23` (Ro Han `ร`).
4. **`_LibThaiWrapper.find_breaks` ctypes `*gen` marshaling (`vith/thai/words.py:75`):**[^src-words]
   - `(ctypes.c_uint32 * (n + 1))(*(ord(ch) for ch in text), 0)` unpacks $n+1$ Python integers as variadic positional arguments into ctypes instead of encoding once with `(text + '\x00').encode('utf-32-le')`.

## Evidence

Measured on `Python 3.15.2`:

| Operation | Current | Optimized | Speedup |
| :--- | ---: | ---: | ---: |
| `_compute_cell_columns` (11k ASCII + tabs) | 2.93 ms | 0.60 ms | **4.9×** |
| `_compute_cell_columns` (11.5k Thai) | 4.84 ms | 2.53 ms | **1.9×** |
| `_LibThaiWrapper.find_breaks` (24k Thai chars) | 6.45 ms | 4.53 ms | **1.42×** |
| `find_next_word_ending` (`e`) near end of 4,000-word line | 0.511 ms/key | $O(\log W)$ `bisect` (~0.01 ms) | **~50×** |
| `find_next_word_beginning` (`w`) near end of 4,000-word line | 0.154 ms/key | $O(\log W)$ `bisect` (~0.01 ms) | **~15×** |

## Fix Direction

1. Fast-path `line.isascii()` in `cell_stops` (`list(range(len(line) + 1))`) and rewrite `_compute_cell_columns` as a single pass with an ASCII+tabs fast path and no per-cluster slices/generators.[^src-clusters]
2. Use `bisect` directly on the cached tuple returned by `_word_spans_for_line` in the cursor-line paths of `find_next_word_beginning`, `find_next_word_ending`, `find_previous_word_beginning`, `find_previous_word_ending`, and `find_boundaries_of_current_word`, and avoid copying/reversing the tuple (`reversed(spans)` for earlier rows).[^src-words]
3. Add `if line.isascii(): return spans` in `_cluster_aligned_spans` and guard `r1_end` behind `ord(line[after_base]) == 0x0E23` in `find_thai_cluster_end`.[^src-words]
4. Encode `(text + '\x00').encode('utf-32-le')` (respecting `sys.byteorder` via `'utf-32-le'`/`'utf-32-be'`) and cast to `ctypes.POINTER(ctypes.c_uint32)` in `_LibThaiWrapper.find_breaks`.[^src-words]
