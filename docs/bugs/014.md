# Cross-line cluster-walk safety relies on `'\n'` taking the `cp<0x300` branch of `is_combining_char`

**Category:** latent correctness · **Area:** `vith/thai.py`, `vith/key_bindings.py` · **Found at:** deep review, hg rev 164 (2026-11-06)

## Summary

The Thai `e`/`E` bindings snap onto cell bases with
`prev_cell_offset(doc.text, cursor + end)`, i.e. the cluster walk runs over
the **multi-line** document text. It terminates at line boundaries only
because `is_combining_char('\n')` short-circuits to `False` (cp 0x0A is below
the 0x300 threshold used before the general width-0 fallback). That invariant
is important but undocumented; reordering the fallback (making the general
`get_cwidth(ch)==0` check generic for all codepoints) would let a backward
walk run across newlines and mis-snap onto the previous line's tail.

## Evidence

* Binding snap: [`vith/key_bindings.py:285-287`](../../vith/key_bindings.py)
  and [`298-300`](../../vith/key_bindings.py) call `prev_cell_offset(doc.text, …)`.
* The guard: [`vith/thai.py:135-136`](../../vith/thai.py) —
  `if cp < 0x300: return False` **before** the
  `unicodedata.category == 'Mn' or get_cwidth(ch) == 0` fallback
  (`vith/thai.py:137`).
* Word spans themselves stay single-line because the chunk regexes bound
  Thai runs to `[\u0e00-\u0eff]+` (no `\n`),
  [`vith/thai.py:456-459`](../../vith/thai.py) — so this is a snap-stage-only
  risk today.

## Impact

No wrong behaviour on current code (verified by probes), but a fragile
invisible invariant supporting multi-line snapping: one future refactor of
`is_combining_char` produces cursor jumps across lines.

## Fix direction

Document the invariant (`'\n'` must classify as non-combining) with a
regression test asserting `prev_cell_offset("ท ab\ncd", col)` never crosses
`\n`, or pass the current line string (and index math) into the snap instead
of `doc.text`.
