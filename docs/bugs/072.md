# `run_reporter` clears stale errors without `invalidate()`, leaving stale pyflakes highlight

**Category:** wrong logic (missed UI invalidation) · **Area:** `vith/editor_buffer.py` (`run_reporter`) · **Found at:** deep review, hg rev 87de3a3 (2026-11-08)

## Summary

`run_reporter` fast-exits for non-Python buffers:

```python
if not checks_python_file(self.location):
    if self.report_errors:
        self.report_errors = []
        self.report_errors_by_line = {}
    return   # no get_app().invalidate()
```

The main (executor) path calls `get_app().invalidate()` in `ready()` when errors change. The early-exit path does not. After `:w newname.txt` (Python → non-Python rename) or after opening a non-Python buffer that inherits a stale index, the red `class:flakeserror` fragments and `ReportMessageToolbar` survive until the next edit triggers a frame.

## Evidence

* [`vith/editor_buffer.py:211-220`](../../vith/editor_buffer.py)[^src-eb] — early-exit clearing without invalidate.
* [`vith/editor_buffer.py:249-264`](../../vith/editor_buffer.py) — `ready()` path does invalidate (asymmetric).
* [`vith/layout.py:780-805`](../../vith/layout.py) — `ReportingProcessor` reads `report_errors_by_line` per frame; stale entries keep marking fragments.

## Impact

Stale red underlines + line-error toolbar after renames or buffer switches; cosmetic but confusing (looks like code errors in non-Python files).

## Fix direction

`invalidate()` after clearing when the list was non-empty (guarded for pre-`Application.run()` calls where `get_app()` may raise `RuntimeError`).
