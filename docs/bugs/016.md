# `run_reporter` binds `loop` only on the PTK3 branch (conditional-definition hazard)

**Category:** latent correctness · **Area:** `vith/editor_buffer.py` (`run_reporter`) · **Found at:** deep review, hg rev 164 (2026-11-06)

## Summary

`loop = asyncio.get_running_loop()` happens inside `if PTK3:`; the later
`loop.call_soon_threadsafe(ready)` / `loop.run_in_executor(...)` reads it only
inside `if PTK3:` branches too. Correctness currently rides on readers being
traceable to the same condition — refactor-friendly code would not.

## Evidence

* Definition: [`vith/editor_buffer.py:208-212`](../../vith/editor_buffer.py).
* Reads: [`vith/editor_buffer.py:250`](../../vith/editor_buffer.py)
  (`loop.call_soon_threadsafe(ready)` inside `if PTK3:`) and
  [`vith/editor_buffer.py:255`](../../vith/editor_buffer.py)
  (`loop.run_in_executor(...)` inside `if PTK3:`).
* mypy accepts this shape (conditional narrowing) — no error, no vigilance.

## Impact

No live defect (PTK2 path imports `run_in_executor`/`call_from_executor`
from `prompt_toolkit.eventloop` instead); a hazard class: refactoring the
two `if PTK3:` blocks independently would produce an unbound local in one
branch.

## Fix direction

Initialize `loop = None` before the PTK3 block (or restructure to a single
dispatch function storing the executor submitter), removing the implicit
pairing.
