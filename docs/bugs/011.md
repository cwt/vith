# Pyflakes error columns are source-space codepoints applied to post-processor fragment indices

**Category:** correctness (inherited) · **Area:** `vith/layout.py`, `vith/reporting.py` · **Found at:** deep review, hg rev 164 (2026-11-06)

## Summary

`ReporterError.start_column/end_column` are computed from pyflakes' source
columns (codepoint space, includes raw `\t`), but `ReportingProcessor` sees
fragments **after** `TabsProcessor` and `ShowTrailingWhiteSpaceProcessor` have
already expanded/replaced characters, so the highlight lands on wrong cells.

## Evidence

* Column derivation: [`vith/reporting.py:68-76`](../../vith/reporting.py) —
  `start_column=message.col` counts codepoints in the raw source line.
* Processor chain order: [`vith/layout.py:573-600`](../../vith/layout.py)
  lists `ShowTrailingWhiteSpaceProcessor`, then `TabsProcessor`, then
  `ReportingProcessor(editor_buffer)`.
* prompt_toolkit's `_MergedProcessor.apply_transformation` chains the listed
  processors **in order** (`prompt_toolkit/layout/processors.py:974-989`, PTK
  3.0.53), so `ReportingProcessor` receives tab-expanded fragments whose
  index space no longer matches source columns; `apply_transformation`
  (`layout.py:633-651`) then indexes `fragments[i]` with those source
  columns directly.
* Behaviour parity note: the original vith instated the same order, so this
  carried over through the P4 rewrite verbatim; `tests/test_layout.py` pins
  the semantics with an identity mapping only (no tab case).

## Impact

`class:flakeserror` highlights misaligned cells on any line containing tabs
or trailing whitespace (the trailing-whitespace processor rewrites them too);
subtle, cosmetic-but-wrong feedback.

## Fix direction

Move `ReportingProcessor` before `TabsProcessor` in the chain, or translate
`error.start_column` through `transformation_input.source_to_display`
before indexing fragments (both inputs are available in PTK 3.0.53).
