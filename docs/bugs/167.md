# Bare `:!{cmd}` never executes

**Category:** commands / shell / asyncio · **Area:** `vith/commands/handler.py` · **Found at:** Round 11 deep correctness audit (2026-11-23, `v0.16.0` / rev 410) · **Fix status:** open

## Summary

`handle_command()` dispatches the bare-shell-command branch by calling
`editor.application.run_system_command(shell_command)`.[^src-handler] In
`prompt_toolkit 3.0.x`, `Application.run_system_command()` is an `async def`:
calling it returns a coroutine object that does nothing until it is awaited or
scheduled on the event loop. The handler neither awaits nor schedules it, so the
coroutine is immediately discarded and no subprocess is ever started.[^src-handler]

## Evidence

Direct probe against the shipped environment (`prompt_toolkit 3.0.53`):

| Probe | Expected | Actual |
| :--- | :--- | :--- |
| `inspect.iscoroutinefunction(Application.run_system_command)` | — | `True` |
| `:!touch /tmp/vith-11-marker` with a marker path that did not exist | marker file created | marker absent; `RuntimeWarning: coroutine 'Application.run_system_command' was never awaited` |

The `:[range]!{cmd}` filter branch and `:[range]w !{cmd}` pipe branch use
`run_shell()` synchronously and are unaffected; only the bare `:!{cmd}` form is
broken.[^src-files]

## Fix Direction

1. Make the shell branch schedule the coroutine on the running loop, e.g.
   `editor.application.create_background_task(editor.application.run_system_command(shell_command))`
   (or the project's equivalent `call_soon_threadsafe`/`ensure_future` helper),
   so the TUI suspends, output is shown, and Enter-to-continue works as in Vim.
2. Add a regression test that runs a bare `:!` command under a real event loop
   and asserts the subprocess side effect (marker file / output) occurred and
   that no `RuntimeWarning` is emitted.
