# `:set` / preview validation drift on `colorcolumn` and integer upper bounds

**Category:** commands / option validation · **Area:** `vith/commands/options.py`, `vith/commands/preview.py` · **Found at:** Round 18 full-project audit (2026-11-24, `v0.16.5`, hg rev `458:d2d313328875`) · **Fix status:** fixed (hg rev 470)

## Summary

`vith/rc_file.py` enforces `_MAX_OPTION_INT = 9999` on integer options and requires strictly positive integers (`number > 0`) in `_parse_colorcolumn`,[^src-rc] but the interactive `:set` handlers and `CommandPreviewer` omit both guards:

1. **Zero and negative `colorcolumn` accepted:** `_set_list_option` (`[int(val) for val in value.split(',')]`) and `CommandPreviewer._preview_list_value` accept `:set cc=-5,0` without error, storing `editor.colorcolumn = [-5, 0]`.[^src-opt][^src-prev]
2. **Unbounded integer options (`tabstop`, `shiftwidth`, `scrolloff`):** `_set_int_option` and `_preview_int_value` check only `number >= minimum` with no upper cap.[^src-opt][^src-prev] Running `:set expandtab tabstop=100000000` succeeds and causes the next `<Tab>` or `>>` keypress to allocate `' ' * 100_000_000` (~100 MB per press).

## Evidence

Live probe against `handle_command`:

* `handle_command(ed, "set cc=-5,0")` → `ed.colorcolumn == [-5, 0]` (no error shown).
* `handle_command(ed, "set ts=100000000")` → `ed.tabstop == 100000000` (no error shown).

## Fix Direction

1. Share `_MAX_OPTION_INT = 9999` (exported from `vith/commands/options.py` and imported by `rc_file.py` and `preview.py`) and reject integer values `> _MAX_OPTION_INT` in `_set_int_option` and `_preview_int_value`.
2. Require `all(n > 0 and n <= _MAX_OPTION_INT for n in numbers)` in `_set_list_option`, `_preview_list_value`, and `rc_file._parse_colorcolumn` (via one shared parser).
3. Add regression tests rejecting `:set cc=0`, `:set cc=-5`, and `:set ts=100000`.
