# `_ThaiTextGate.note` scans the whole buffer per keystroke on non-ASCII non-Thai files, and word motions check `doc.text.isascii()`

**Category:** unoptimized algorithm · **Area:** `vith/thai.py`, `vith/editor_buffer.py` · **Found at:** deep review, hg rev 191 (2026-11-07)

## Summary

Two fast-path checks in `vith/thai.py` degrade from $O(1)$ / $O(\text{line})$ to $O(N_{\text{doc}})$ when a buffer contains non-ASCII characters:

1. **Whole-buffer regex scan per keystroke on non-ASCII, non-Thai files** ([`vith/thai.py:904-909`](../../vith/thai.py)[^src-thai], [`vith/editor_buffer.py:82`](../../vith/editor_buffer.py)[^src-eb]):
   `EditorBuffer._create_buffer` registers `text_changed` to call `note_document_text(self.buffer.text)` on every edit. Inside `_ThaiTextGate.note(self, text)`:
   ```python
   def note(self, text: str) -> None:
       if self.value or not text or text.isascii():
           return
       if _HAS_THAI_RE.search(text):
           self.value = True
   ```
   When editing a large file that contains even a single non-ASCII, non-Thai character (such as `—`, `•`, `©`, `é`, or emoji — e.g. `docs/speed_latency_plan.md`), `self.value` remains `False` and `text.isascii()` is `False` (CPython's cached UTF-8 representation flag), so `_HAS_THAI_RE.search(text)` linearly scans the **entire buffer** on every single keystroke.
2. **Whole-document `doc.text.isascii()` in line-local word motions** ([`vith/thai.py:562, 601, 646, 683, 697`](../../vith/thai.py)[^src-thai]):
   All five patched `Document` word-motion methods (`find_next_word_beginning`, `find_next_word_ending`, `find_previous_word_beginning`, `find_start_of_previous_word`, `find_previous_word_ending`) check:
   ```python
   if not _THAI_GATE.value or doc.text.isascii():
       return _ORIG_DOC_FIND_...(doc, count=count, WORD=WORD, pattern=pattern)
   ```
   Once `_THAI_GATE.value` is `True` (because any buffer in the session has seen a Thai character, or the current file has one Thai comment at line 5,000), pressing `w`/`b`/`e` on pure-ASCII lines still enters `_iter_word_Boundary_forward` / `_iter_word_boundary_backward` and runs `_has_thai_or_lao(slice_text)` instead of checking `doc.current_line.isascii()`.

## Evidence

* [`vith/thai.py:904-909`](../../vith/thai.py)[^src-thai]:
  ```python
  def note(self, text: str) -> None:
      if self.value or not text or text.isascii():
          return
      if _HAS_THAI_RE.search(text):
          self.value = True
  ```
* [`vith/editor_buffer.py:76-83`](../../vith/editor_buffer.py)[^src-eb]:
  ```python
  def text_changed(_):
      self.has_unsaved_changes = True
      note_document_text(self.buffer.text)
      self.run_reporter()
  ```

## Impact

* Typing in a multi-megabyte file containing any non-ASCII punctuation (`—`, `…`) or Western/CJK Unicode characters scans the full document text with `_HAS_THAI_RE` on every keystroke.
* Word motions on ASCII lines in mixed ASCII/Thai sessions skip the native C `re` fast path.

## Fix direction

1. On `text_changed`, pass only `self.buffer.document.current_line` (or the edited line) to `note_document_text(...)`, while scanning the full `text` only once in `EditorBuffer.__init__` / `EditorBuffer.read`.
2. In `find_start_of_previous_word` (which never crosses lines) and the single-line cases of `find_next_word_*` / `find_previous_word_*`, check `doc.current_line.isascii()` before falling back to `_iter_word_boundary_*`.
