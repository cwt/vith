# `create_tab()` on an empty arrangement creates two tabs

**Category:** window arrangement / tabs · **Area:** `vith/window_arrangement.py` · **Found at:** Round 11 deep correctness audit (2026-11-23, `v0.16.0` / rev 410) · **Fix status:** open

## Summary

`WindowArrangement.create_tab()` resolves the target editor buffer via
`_get_or_create_editor_buffer()`, which calls `_add_editor_buffer()`; that
method already creates an initial `TabPage` when `tab_pages == []`.[^src-wa]
`create_tab()` unconditionally appends another `TabPage`, so calling the public
API before any file/buffer is loaded produces two tabs backed by a single
editor buffer. Normal startup (`load_initial_files`) creates the first tab
first, which is why the test suite misses this.

## Evidence

Fresh `Editor` instance with an empty arrangement:

| Observable | Expected | Actual |
| :--- | :--- | :--- |
| tabs after `create_tab('somefile.py')` | 1 | **2** |
| `active_tab_index` | 0 | **1** |
| `len(editor_buffers)` | 1 | 1 |

Both tabs display the same buffer, so closing/tab navigation from that state is
inconsistent.

## Fix Direction

1. In `create_tab()`, capture whether `tab_pages` was empty before resolving the
   buffer; if so, reuse the tab created by `_add_editor_buffer()` instead of
   appending a second one. Alternatively, teach `_add_editor_buffer()` not to
   create a tab and have all callers establish one explicitly.
2. Add a regression test for `create_tab()` on a fresh arrangement asserting
   exactly one tab and the expected active index, plus a test for the
   already-populated arrangement (unchanged behavior).
