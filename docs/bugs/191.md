# U+0EC7 is misclassified as a zero-width mark

**Category:** Thai / Unicode classification · **Area:** `vith/thai/classify.py` · **Found at:** Round 11 deep correctness audit (2026-11-23, `v0.16.0` / rev 410) · **Fix status:** fixed
> **Resolution note (2026-11-23):** Removed unassigned `U+0EC7` from `_THAI_COMBINING_CPS`; the general width fallback now applies.


## Summary

`classify.py` includes `0x0EC7` (commented `MAITAIKHU`) in
`_THAI_COMBINING_CPS`.[^src-classify] In the current Unicode data this codepoint
is unassigned (`Cn`) with terminal width 1; the real Lao marks in that region
start at `U+0EC8`. All other 33 entries in the table are genuine `Mn` marks.
Because `is_combining_char()` short-circuits for the whole `0x0E00–0x0EFF`
range,[^src-classify] the general `Mn` / `get_cwidth()` fallback never runs,
so `next_cell_offset()` skips the codepoint and `snap_to_cell_start()` walks
back over it — treating a width-1 character as attached to the preceding cell.

## Evidence

| Check | Expected | Actual |
| :--- | :--- | :--- |
| `unicodedata.category(chr(0x0EC7))` | `Mn` if it were a mark | `Cn` |
| `get_cwidth(chr(0x0EC7))` | 0 if zero-width | `1` |
| `is_thai_combining(0x0EC7)` | `False` | `True` |
| `is_combining_char(chr(0x0EC7))` | `False` | `True` |

Practical impact is low because the codepoint is unassigned, but it violates
the documented classification contract and is a latent trap if Unicode ever
assigns it as a spacing character.

## Fix Direction

1. Remove `0x0EC7` from `_THAI_COMBINING_CPS` (and correct/remove the stale
   `MAITAIKHU` comment), or let the general `Mn`/`get_cwidth()` fallback decide
   for unassigned codepoints instead of short-circuiting the entire block.
2. Add a table-consistency test asserting every entry in `_THAI_COMBINING_CPS`
   is `unicodedata.category(...) == 'Mn'` in the running Python build (or is
   explicitly whitelisted with a documented rationale).
