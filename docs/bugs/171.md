# Generic render exceptions are misclassified as transient

**Category:** live render / error handling · **Area:** `vith/render.py` · **Found at:** Round 11 deep correctness audit (2026-11-23, `v0.16.0` / rev 410) · **Fix status:** fixed
> **Resolution note (2026-11-23):** Generic renderer exceptions are no longer classified as transient `ParseIncompleteError`; they now show a visible diagnostic.


## Summary

Both render paths catch a bare `Exception` and set `incomplete = True`:[^src-render]

* `render_sync()` — `self._apply_error(version, f'Render error: {exc}', incomplete=True)`;
* `in_executor()` — `err_msg = f'Render error: {exc}'; incomplete = True`.

`_apply_error()` responds to `incomplete=True` plus `_has_good_render` by
keeping the old preview and only marking the title `• stale`, with **no message
shown**.[^src-render] `docs/live_render.md` §6.1 reserves that behavior
specifically for `ParseIncompleteError` (mid-edit JSON/broken RST/timed-out
CLI).[^src-doc] A permanent, content-dependent library error — such as the CSV
`MarkupError` in [169](169.md) — is therefore indistinguishable from "the user
is still typing" and the user has no way to learn why updates stopped.

## Evidence

* `render_document('a,b\n[bold]X,[/]Y\n', filetype='csv')` raises
  `rich.errors.MarkupError`.
* Through the controller, this lands in the generic `except Exception` branch,
  sets `incomplete=True`, and leaves the previous table on screen under a
  `• stale` title indefinitely (no red diagnostic line).
* Same mechanism applies to any future Rich/Pygments/upstream regression.

## Fix Direction

1. Reserve `incomplete=True` for `ParseIncompleteError` only. For generic
   exceptions, call `_apply_error(..., incomplete=False)` so the red diagnostic
   line is shown, and reset `_has_good_render` ([172](172.md)).
2. Add tests asserting that a `MarkupError`-style content failure produces a
   visible diagnostic, while a mid-edit `ParseIncompleteError` still retains
   the stale render (existing behavior).
