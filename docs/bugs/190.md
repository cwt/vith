# Reporter can be permanently disabled by a worker exception

**Category:** reporting / concurrency · **Area:** `vith/editor_buffer.py` · **Found at:** Round 11 deep correctness audit (2026-11-23, `v0.16.0` / rev 410) · **Fix status:** fixed
> **Resolution note (2026-11-23):** The reporter worker catches exceptions and always schedules `ready()`, so later runs can recover.


> **Verification note:** this is a structural finding from code review. No
> standard-library/pyflakes input was found that raises inside `report()`, so
> it is recorded as `verified: unverified` rather than a live reproduction.

## Summary

`EditorBuffer.run_reporter()` sets `self._reporter_is_running = True`, submits
`report(...)` to the executor, and only clears the flag inside the `ready()`
callback.[^src-eb] If the worker raises any unexpected exception (a future
pyflakes/plugin bug, a pathological source construct, or a third-party reporter
error), the future's exception is never observed — there is no done-callback
and the future is not awaited — so `ready()` is not scheduled. The flag then
stays `True` forever, every subsequent `run_reporter()` only sets
`_run_reporter_again`, and diagnostics for that buffer are frozen for the rest
of the session (plus an "exception was never retrieved" warning).

## Fix Direction

1. Attach a done-callback to the executor future (or wrap `report()` in a
   `try/finally` that calls `loop.call_soon_threadsafe(ready, ...)` on both the
   success and failure paths) so `_reporter_is_running` is always cleared and
   `_run_reporter_again` is honored.
2. Add a regression test that monkeypatches `report()` to raise and asserts a
   later `run_reporter()` still produces diagnostics.
