# TOML config bypasses option validation and mis-detects top-level keys

**Category:** robustness / configuration · **Area:** `vith/rc_file.py` (`apply_toml_config`, `run_rc_file`) · **Found at:** Round 8 full re-audit, 2026-11-19, hg rev 358 (`ff583fcf26ba`) · **Fix status:** open

## Summary

The TOML path is advertised as the primary configuration format, but it
applies values with raw `setattr()` and only converts `[tabstop]` entries
inside a try/except. The `:set` command path validates names, types, and
ranges; TOML does not.

Two concrete consequences:

1. **Uncaught conversion error.**
   `colorcolumn = ["x"]` reaches `[int(x) for x in val]` and raises
   `ValueError`. `apply_toml_config()` is called directly from
   `run_rc_file()` and from `source_file()`, neither of which catches it, so
   the editor fails to start (or `:source` aborts) with a Python traceback.

2. **Wrong types accepted.**
   `tabstop = "four"` is assigned to `editor.tabstop`; later
   `Editor.get_filetype_tabstop()` returns the string, `TabsProcessor`
   performs arithmetic on it, and `_get_buffer_tabstop()`/`_insert_indentation`
   use it for `' ' * width`. A negative or zero value bypasses the
   `tabstop >= 1` buffer setter until the first affected render/insert. A
   huge integer (e.g. `999999999`) is accepted and can allocate a huge tab
   expansion.

## Evidence

* Raw application loop and colorcolumn conversion:
  [`vith/rc_file.py:236-254`](../../vith/rc_file.py#L236-L254).
* Probe 1 (`colorcolumn = ["x"]`):

  ```text
  run_rc_file(...) / :source -> ValueError: invalid literal for int() with base 10: 'x'
  ```

  (The same input under `:set cc=x` correctly shows a message and leaves the
  option unchanged.)

* Probe 2 (`tabstop = "four"`):

  ```text
  run_rc_file -> True, editor.tabstop == 'four'
  ```

  The next tab-sensitive operation either raises `TypeError` or computes a
  nonsensical width.

* Probe 3 (`~/.vithrc` containing only `colorscheme = "monokai"`):
  `tomllib.loads()` succeeds, but the detection predicate checks only
  `editor` / `tabstop` / `filetype_tabstops` / `hooks` /
  `_CONFIG_OPTION_MAP` keys, so `colorscheme` and `colorcolumn` are not
  recognized. The file falls through to `_run_python_rc_file()`, where
  `colorscheme = "monokai"` is a harmless Python assignment; the intended
  option is never applied and no error is shown.

## Impact

* A typo in `config.toml` can prevent the editor from starting.
* A wrong tabstop type reaches rendering and cannot be cleared through the
  normal `:set` validation path.
* `~/.vithrc` users get silent no-ops for two supported top-level keys.

## Fix direction

1. Reuse the `SET_TOGGLE_GROUPS`/`SET_INT_OPTIONS`/`SET_LIST_OPTIONS` catalog
   (and `set_filetype`/`set_fileencoding` handlers) to validate TOML options:
   boolean types, integer bounds (`1..9999` for tabstop/shiftwidth), encoding
   names, lexer aliases, and colorcolumn positivity.
2. Convert all errors into `error_handler` messages instead of uncaught
   exceptions; keep applying the remaining valid options.
3. Add `colorscheme`, `colo`, and `colorcolumn` to the non-`.toml`
   TOML-detection predicate (or simply treat any successful
   `tomllib.loads()` containing at least one known key as TOML).
4. Add tests for invalid colorcolumn, string tabstop, out-of-range tabstop,
   and `.vithrc` top-level colorscheme/colorcolumn.
