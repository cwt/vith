# `:b` requires an exact location match but its completer promises substring, and indices are 0-based

**Category:** wrong logic / UX mismatch · **Area:** `vith/window_arrangement.py` (`go_to_buffer`), `vith/commands/completer.py`, `vith/layout.py` · **Found at:** deep review, hg rev 87de3a3 (2026-11-08)

## Summary

Three places disagree about what `:b <name>` means:

* `BufferNameCompleter.get_completions` yields when `text in location` (substring).
* `WindowArrangement.go_to_buffer` jumps only when `eb.location == buffer_name` (exact).
* Numeric matching is `int(buffer_name) == i` with `i` from `enumerate(editor_buffers)` (0-based), and `BufferListOverlay` displays the same 0-based index (`%3i`). Vim buffer numbers are 1-based.

Completing a substring then pressing Enter therefore does nothing, and `:b 1` jumps to the *second* buffer.

## Evidence

* [`vith/commands/completer.py:27-44`](../../vith/commands/completer.py)[^src-comp] — substring completer.
* [`vith/window_arrangement.py:369-378`](../../vith/window_arrangement.py)[^src-wa] — exact-or-0-based-index `go_to_buffer`.
* [`vith/layout.py:282-296`](../../vith/layout.py) — overlay renders `info.index` directly.

## Impact

`:b <substring>` (the documented completion flow) silently fails; `:b <n>` is off-by-one vs Vim muscle memory.

## Fix direction

Resolve in order: exact location → unique substring (error on ambiguous, as Vim does) → 1-based numeric index. Align overlay display with the same numbering (or label clearly as 0-based if kept intentionally).
