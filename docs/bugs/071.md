# Miscellaneous Vim-semantics deviations (`r` count, file-explorer open, `is_combining_char`, cold-text undo cursor, private `_search`)

**Category:** wrong logic (grouped lows, as in [054](054.md)) · **Area:** `vith/key_bindings.py`, `vith/thai.py`, `vith/cold_text.py`, `vith/commands/commands.py` · **Found at:** deep review, hg rev 87de3a3 (2026-11-08) · **Re-validated:** 2026-11-08 at hg rev 251 (tip; code identical to the audit revision)

## Summary

| # | Location | Defect | Validated |
|---|---|---|---|
| 1 | `key_bindings.py:115-130` | `autocomplete_or_indent` docstring says “do autocompletion, otherwise indent” — code only inserts a tab/space (filter is `whitespace_before_cursor_on_line`). Name + docstring lie; no completion is wired. | CONFIRMED |
| 2 | `key_bindings.py:242-256` | `2rX` deletes `event.arg` clusters and inserts `event.data * event.arg` (`"XX"`), backing up one cluster. Vim replaces N chars with *one* char. | CONFIRMED |
| 3 | `key_bindings.py:188-201` | File-explorer `<Enter>` opens the whole `current_line` (`:193`), not the word under cursor. Filenames with spaces open as one path. | CONFIRMED |
| 4 | `thai.py:173-193` | `is_combining_char(ch: str)` reads only `ch[0]` (`:188`, `:193`) but suggests a string API. Cluster strings silently ignore the suffix (runtime check: `is_combining_char('ที') → False`, `is_combining_char('ีx') → True`). No `len(ch) == 1` assert or docstring note. | CONFIRMED |
| 5 | `cold_text.py:144-147, 192-206, 213-217` | The original “cursor-only optimization never hits” claim is **refuted** — the `update_top_cursor` branch hits on every cursor-only save (vi motions trigger `save_to_undo_stack` via ptk's default `save_before`, and it is pinned by `tests/test_cold_text.py:93-101`). The reproducible defect in the same cluster is cursor restoration: `update_top_cursor` rewrites only `self._meta[-1]` (`:144-147`) while the compressed item tuple pushed at `:135` keeps the old cursor; `undo` pops the item (`text, cursor_position, _t… = undo_stack.pop()`, `:213-216`) and restores the **old** cursor — the cursor recorded by a cursor-only save is never restored. The history-traversal variant the doc worried about is currently theoretical (editor `ColdTextBuffer`s carry no `history=`, `editor_buffer.py:58-67`, so `working_index` never changes in-app). | CORRECTED (new defect) |
| 6 | `commands.py:834` | `substitute` calls private `buffer._search(...)` (the public surface is `search`/`search_next`). Breaks on prompt_toolkit rename (same fragility class as [064](064.md)). | CONFIRMED |
| 7 | `thai.py:710-711` (and `:614-615`) | `count < 0` delegates to `find_next_word_ending` without `include_current_position`. After validation: this matches upstream prompt_toolkit `document.py:637-638` verbatim (inherited, not vith-introduced), and no vi handler can pass a negative count here (`ge`/`gE` text objects take a positive digit arg, `vi.py:1813-1835`) — a dead branch rather than a live semantics break. | RECLASSIFIED |

## Impact

Each is cosmetic or edge-case; together they are the “Vim-parity paper cuts” a daily driver feels. Row 5 additionally causes real wrong-cursor undo for the cursor-only path.

## Fix direction

Rename/document (1); align `r` count with Vim + test; open the word under cursor in the file explorer; assert `len(ch) == 1` in (4); fix `update_top_cursor` to rewrite the popped item tuple as well (or push a fresh entry on version bump) and add a cursor-only undo test (5); use the public search API in (6); remove or document the negative-count delegate in (7) as upstream parity.
