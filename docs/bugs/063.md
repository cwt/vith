# `$` ignores `event.arg`: `3$` moves to the current line instead of three lines down

**Category:** wrong logic / Vim semantics · **Area:** `vith/key_bindings.py` (`move_to_end_of_line_cell`) · **Found at:** deep review, hg rev 87de3a3 (2026-11-08)

## Summary

The Phase 3 cell-cluster override for `$` rebases the cursor to the start of the last cell cluster on the *current* line, but never reads `event.arg`. Vim `$` with a count (`3$`) moves to end-of-line `count` lines down. Vith’s override regresses that: `3$` stays on the current line.

Every sibling motion (`x`, `X`, `s`, `r`, `~`, `e`, `E`) reads `event.arg`; `$` is the only one that does not.

## Evidence

* [`vith/key_bindings.py:276-287`](../../vith/key_bindings.py)[^src-kb]:
  ```python
  @kb.add('$', filter=(vi_navigation_mode | vi_selection_mode) & ...)
  def move_to_end_of_line_cell(event):
      buff = event.current_buffer
      doc = buff.document
      line = doc.current_line
      target_col = prev_cell_offset(line, len(line), 1)
      buff.cursor_position += target_col - doc.cursor_position_col
  ```
* `event.arg` is never referenced in the handler body, unlike `next_cell_offset(line, col, event.arg)` in `delete_cell_clusters` ([029](029.md)-style dedup) or `find_next_word_ending(count=event.arg)` for `e`/`E`.

## Impact

* `3$` (bare `$` with count) no-ops vertically; users expect cursor on line `+2`.
* Operator-pending `d3$`/`y3$` are unaffected (they fall through to prompt_toolkit’s `vi.py`), so the bug only shows on bare `$` — which makes it easy to miss.

## Fix direction

Compute `target_row = min(len(doc.lines) - 1, doc.cursor_position_row + event.arg - 1)`, resolve that row’s last cell start via `prev_cell_offset(doc.lines[target_row], len(...), 1)`, then `translate_row_col_to_index` to the absolute target. Keep the existing `vi_waiting_for_text_object_mode` exclusion so `d$` still delegates to `vi.py`.
