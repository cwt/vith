# `$` drops its count and `e`/`E` pass the whole document to `prev_cell_offset`

**Category:** wrong logic / Vim semantics + fragile contract · **Area:** `vith/key_bindings.py` (Phase-3 cell-cluster motion overrides) · **Found at:** deep review, hg rev 87de3a3 (2026-11-08) · **Re-validated:** 2026-11-08 at hg rev 251 (tip; code identical to the audit revision)

## A. `$` ignores `event.arg`: `3$` stays on the current line (high)

### Summary

The Phase 3 cell-cluster override for `$` rebases the cursor to the start of the last cell cluster on the *current* line, but never reads `event.arg`. Vim `$` with a count (`3$`) moves to end-of-line `count` lines down. Vith's override regresses that: `3$` stays on the current line.

Every sibling motion (`x`, `X`, `s`, `r`, `~`, `e`, `E`) reads `event.arg`; `$` is the only one that does not.

### Evidence

* [`vith/key_bindings.py:276-287`](../../vith/key_bindings.py)[^src-kb]:
  ```python
  @kb.add('$', filter=(vi_navigation_mode | vi_selection_mode) & ...)
  def move_to_end_of_line_cell(event):
      buff = event.current_buffer
      doc = buff.document
      line = doc.current_line
      target_col = prev_cell_offset(line, len(line), 1)
      buff.cursor_position += target_col - doc.cursor_position_col
  ```
* Whole-file search: the handler body contains zero `event.arg` references, while `s` (`:237`), `r` (`:251`, `:254`), `~` (`:269`), `x`/`X` (`:42`, `:44`) and `e`/`E` (`:293`) all read it.
* Operator-pending `d3$`/`y3$` are unaffected — the binding filter excludes `vi_waiting_for_text_object_mode`, so those fall through to prompt_toolkit's `vi.py` (`text_object("$")`), which is exactly why the regression is easy to miss.

## B. `e`/`E` pass the whole document as a single “line” to `prev_cell_offset` (medium)

### Summary

`e`/`E` compute an exclusive word end via `doc.find_next_word_ending`, then step back one cell with `prev_cell_offset(doc.text, absolute_end, 1)`. The function contract is `(line, col)` — a single line and a line-local column. Passing the entire multi-line `doc.text` and an absolute offset works only because combining marks never attach across `\n` ([014](014.md) invariant). It also forces a whole-document `isascii()` scan on every `e`/`E` press, defeating the per-line ASCII fast-path the Thai word motions preserve ([056](056.md), closed).

### Evidence

* [`vith/key_bindings.py:289-295`](../../vith/key_bindings.py):
  ```python
  def _move_to_end_of_word_cell(event, WORD):
      end = doc.find_next_word_ending(count=event.arg, WORD=WORD)
      if end:
          buff.cursor_position = prev_cell_offset(doc.text, buff.cursor_position + end, 1)
  ```
* [`vith/thai.py:279-283`](../../vith/thai.py)[^src-thai] — contract: “Move `count` visual cell clusters backward from `col` **within `line`**”; every other call site passes line-local values (`key_bindings.py:42`, `thai.py:636`, `thai.py:1422`).
* [`vith/thai.py:286-287`](../../vith/thai.py) — `if line.isascii(): return max(0, col - count)` — with `doc.text` passed this is a whole-document scan on every `e`/`E`.
* [`vith/thai.py:289-296`](../../vith/thai.py) — backward walk `idx -= 1; while idx > 0 and is_combining_char(line[idx]): idx -= 1` — no newline stop; correctness depends on `\n` never classifying as combining.
* The reliance is documented, not hidden: `thai.py:178-184` states the cluster scanners “rely on newline never behaving like a combining mark”, pinned by `tests/test_thai.py:684-709`.

## Impact

* **A:** `3$` (bare `$` with count) no-ops vertically; users expect the cursor three lines down on the line end.
* **B:** every `e`/`E` press pays at least two whole-document scans (the motion's own `doc.text.isascii()` at `thai.py:616` and `prev_cell_offset`'s), and semantic correctness rests on the standing `\n` invariant rather than the function contract.

## Fix direction

* **A:** compute `target_row = min(len(doc.lines) - 1, doc.cursor_position_row + event.arg - 1)`, resolve that row's last cell start via `prev_cell_offset(doc.lines[target_row], len(...), 1)`, then `translate_row_col_to_index` to the absolute target. Keep the `vi_waiting_for_text_object_mode` exclusion so `d$` still delegates to `vi.py`.
* **B:** translate the absolute end to `(row, col)` via `doc.translate_index_to_position(buff.cursor_position + end)`, call `prev_cell_offset(doc.lines[row], col, 1)`, then `doc.translate_row_col_to_index(row, new_col)` — restores the per-line fast-path and removes the invariant reliance.

## Validation (2026-11-08, hg rev 251)

* **A — CONFIRMED**: handler is `event.arg`-free; all six sibling overrides read it (line refs exact, no drift).
* **B — PARTIALLY CONFIRMED**: the contract violation, whole-document scans and `\n`-invariant reliance are real, but the originally claimed failure (“a word ending at column 0 of the next line lands the cursor on the previous line”) is **not reproducible**: `find_next_word_ending` returns ends strictly inside a word's own line (Thai per-line spans via `_word_spans_for_line`, `thai.py:563/531-543/650`; the vanilla ASCII word regexes cannot match `\n`, `document.py:28/36/577-607`), and `prev_cell_offset` stops at the first non-combining character, so the backward walk never reaches the line boundary (see the boundary-case comment at `tests/test_thai.py:698-702`). B is re-scoped from a cursor-mis-landing bug to contract fragility + a per-keystroke whole-document cost.
