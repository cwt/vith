# `immediate=True` is dropped while a render is in flight

**Category:** live render / debounce · **Area:** `vith/render.py` · **Found at:** Round 11 deep correctness audit (2026-11-23, `v0.16.0` / rev 410) · **Fix status:** open

## Summary

`LiveRenderController.schedule()` handles the in-flight case with:[^src-render]

```python
if self._in_flight:
    self._pending = True
    return
```

The `immediate` keyword is not recorded, and the follow-up `self.schedule()` in
`finish()`[^src-render] is called without it. Callers that explicitly request
an immediate refresh — re-running `:render` (`open_or_update_live_render`),
`:set filetype=…`,[^src-options] and the startup `pre_run` hook[^src-editor] —
therefore wait out the full debounce window after any in-flight render.
`docs/live_render.md` documents the immediate-refresh contract (§4, §6).[^src-doc]

## Evidence

Code-path verification: with a slow render in flight (large Markdown or the
5-second external-command path), `:render` / `:set ft=markdown` set `_pending`
but no `_pending_immediate`; `finish()` calls `schedule()` with `immediate`
defaulting to `False`, so `delay = debounce_s` instead of `0`. Impact is bounded
by `render_debounce_ms` (default 150 ms), hence low severity.

## Fix Direction

1. Add `self._pending_immediate = False` state; in the `_in_flight` branch OR
   the `immediate` argument into it; in `finish()` call
   `self.schedule(immediate=self._pending_immediate)` and reset the flag.
2. Add an async test with a deliberately slow renderer asserting that an
   immediate re-render request issued mid-flight is dispatched with zero
   delay.
