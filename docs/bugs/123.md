# `:s` regex has no catastrophic-backtracking guard

**Category:** security / robustness · **Area:** `vith/commands/commands.py` · **Found at:** upstream triage 2026-11-09 (`prompt-toolkit/pyvim#159`) · **Fix status:** fixed

## Summary

`:s/(a+)+$/x` on a 30-char line freezes the editor; the pattern goes straight to the backtracking `re` engine.

## Evidence

* `substitute()` in `vith/commands/commands.py:698-740`[^src-cmd] does `re.compile(search)` then `pattern.sub(replace, original, count=sub_count)` per line — no timeout, length cap, or nested-quantifier check. `re.error` is caught (`:701-704`, `:731-744`), but catastrophic patterns compile cleanly and only explode at match time.
* Upstream PoV: 20 `a`s ≈ 0.09 s, 25 ≈ 2.7 s, 30 ≈ 88 s.

## Impact

* Self-DoS: one accidental paste of an ambiguous pattern hangs the TUI (no data loss, but the session must be killed). No remote vector — the attacker is the local operator.

## Fix

* `vith/commands/commands.py` rejects nested-quantifier patterns (`_UNSAFE_NESTED_QUANTIFIER` over `_strip_regex_literals()`, which removes escapes and `[...]` classes first) with `Unsafe pattern (nested quantifier)` before compiling — no buffer mutation, no history update. Safe grouped patterns (`(foo|bar)`, `[a+]+`, escaped parens) still substitute.
* Regression tests in `tests/test_substitute.py`: rejection of `(a+)+$` / `([a-z]+)*$` / `(\w+\s?)+` / `(a|a?)+` with buffer untouched, plus allow-list cases.
