# `FileIO.write` omits `newline=''` on Windows (`\r\r\n` / doubled newlines on save)

**Category:** I/O / Windows line-ending corruption · **Area:** `vith/io/backends.py` (`FileIO.write`) · **Found at:** user field report on Windows 11 editing `~/.config/vith/config.toml` (`v0.16.4` / rev 444) · **Fix status:** fixed

> **Resolution note (2026-11-23):** Passed `newline=''` to `io.open(location, 'w', encoding=encoding, newline='')` in `FileIO.write` (`vith/io/backends.py`) so line endings already serialized by `EditorBuffer.write` / `_file_payload` (`\r\n`, `\n`, `\r`) are written verbatim without OS newline translation. Pinned with regression tests in `tests/test_io_backends.py` (asserting `newline=''` on `io.open` so the guard holds on POSIX CI as well, plus byte-level `dos`/`unix`/`mac` write checks) and `tests/test_editor_buffer.py` (multi-cycle CRLF open/save round-trip).

## Summary

Editing a CRLF file such as `~/.config/vith/config.toml` in `vith` on Windows caused every line ending to be written as **`\r\r\n`** (`0D 0D 0A`), doubling blank lines on every reload/save cycle:[^src-backends]

1. `FileIO.read()` opens the file in binary mode (`'rb'`), returning the exact `\r\n` text.
2. `EditorBuffer._read()` detects `fileformat = 'dos'` and normalizes `\r\n` to `\n` in the in-memory buffer.[^src-eb]
3. `EditorBuffer.write()` (and `_file_payload()` in `vith/commands/files.py`) explicitly serializes `\n` back to `self.line_ending()` (`'\r\n'` for `dos`, `'\n'` for `unix`, `'\r'` for `mac`).
4. `FileIO.write()` then called `io.open(location, 'w', encoding=encoding)` with Python's default `newline=None`. On Windows (`os.linesep == '\r\n'`), `io.TextIOWrapper` translates every `'\n'` written into `'\r\n'`:
   * `dos` buffers (`'\r\n'`) were written as **`'\r\r\n'`** (`0D 0D 0A`).
   * `unix` buffers (`'\n'`) were silently converted to **`'\r\n'`**.
5. On the next open, `EditorBuffer._read()` executes `text.replace('\r\n', '\n').replace('\r', '\n')` (and Python universal-newlines readers treat `\r` and `\r\n` as separate line breaks), turning every `\r\r\n` into `\n\n` — doubling the number of newlines on every open/save cycle (`1 -> 2 -> 4 -> ...`).

`FileIO.append()` (`open(..., 'ab')`) and `GZipFileIO.write()` (`gzip.open(..., 'wb')`) already wrote encoded bytes directly and were unaffected. Because `os.linesep == '\n'` on Linux/macOS, the missing `newline=''` parameter went undetected in POSIX test runs.

## Evidence

* Observed bytes in the user's `~/.config/vith/config.toml` (94 bytes: 12 CR, 6 LF):
  ```text
  5B 65 64 69 74 6F 72 5D 0D 0D 0A ...
  [editor]\r\r\n
  variation_selector_always_wide = true\r\r\n
  \r\r\n
  [hooks]\r\r\n
  #enabled = ["sun-os.py"]\r\r\n
  \r\r\n
  ```
* Running `pytest` on Windows (`win32`, Python 3.15.2) before the fix failed 14+ write tests directly with `\r\r\n` / `\n\n` assertions, including:
  * `test_crlf_fileformat_round_trips_on_write`: `assert b'one\r\r\ntwoX\r\r\n' == b'one\r\ntwoX\r\n'`
  * `test_lf_and_no_eol_preserved_and_set_fileformat`: `assert b'one\r\ntwo' == b'one\ntwo'`
  * `test_editor_buffer_preserves_trailing_newline_presence`: `assert 'line 1 modified\n\nline 2\n\n' == 'line 1 modified\nline 2\n'`
* After passing `newline=''` in `FileIO.write`, all 26 tests in `tests/test_editor_buffer.py` and all write tests across `test_write_commands.py`, `test_ex_commands.py`, `test_key_bindings_fixes.py`, `test_quit_and_goto.py`, `test_startup_io.py`, and `test_round9_dedup.py` pass on Windows, with `ruff check` and `mypy` clean.

## Fix Direction

1. Pass `newline=''` to `io.open(location, 'w', encoding=encoding, newline='')` in `FileIO.write` (`vith/io/backends.py`).[^src-backends]
2. Assert `kw.get('newline') == ''` in `test_fileio_uses_io_open` so the fix cannot silently regress on POSIX CI, and add byte-level `FileIO.write` (`dos`/`unix`/`mac`) and multi-cycle CRLF `EditorBuffer` round-trip tests.[^src-tests-io][^src-tests-eb]
