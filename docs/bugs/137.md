# Non-UTF-8 shell output crashes the new Ex shell commands

**Category:** robustness / crash · **Area:** `vith/commands/commands.py` (`_read_shell_text`, `_write_pipe_shell`, `filter_range_command`) · **Found at:** Round 8 full re-audit, 2026-11-19, hg rev 358 (`ff583fcf26ba`) · **Fix status:** open

## Summary

Three new command paths invoke a shell with `text=True` and no encoding or
error policy:

* `:r !cmd` / `:read !cmd` — [`_read_shell_text`, `commands.py:572-593`](../../vith/commands/commands.py#L572-L593)
* `:[range]w !cmd` — [`_write_pipe_shell`, `commands.py:806-836`](../../vith/commands/commands.py#L806-L836)
* `:[range]!cmd` — [`filter_range_command`, `commands.py:954-969`](../../vith/commands/commands.py#L954-L969)

`subprocess.run(text=True)` decodes the child's combined stdout/stderr using
the locale encoding with `errors='strict'`. Shell output is arbitrary bytes
(e.g. a binary-safe tool, a Latin-1 filename, or a program that intentionally
writes `0xFF`). The decode error is not among the caught
`TimeoutExpired`/`OSError` exceptions, so it propagates through
`handle_command()` and aborts the TUI.

The reverse direction is also affected: `_write_pipe_shell` encodes the
payload to stdin using the locale encoding, so a Thai/other non-ASCII payload
raises `UnicodeEncodeError` under a non-UTF-8 locale.

## Evidence

Probe with a command that emits one invalid UTF-8 byte:

```text
:r !printf '\xff\n'            -> UnicodeDecodeError: 'utf-8' codec ...
:%!printf '\xff\n'             -> UnicodeDecodeError: 'utf-8' codec ...
:w !cat >/dev/null; printf '\xff'
                                -> UnicodeDecodeError: 'utf-8' codec ...
```

All three are machine-confirmed; each exception escaped the handler. The
`except OSError` clauses do not cover `UnicodeDecodeError`
(subclass of `UnicodeError`, not `OSError`).

## Impact

* Any command that prints non-UTF-8 bytes can crash the whole editor.
* `:w !` is particularly dangerous because the shell command may already have
  consumed/modified data before the decode failure is reported.
* Under a C/POSIX locale, piping a buffer containing Thai text already fails
  on the input side.

## Fix direction

1. Centralize shell execution in one helper used by all four call sites
   (read, filter, write-pipe, and possibly `:!`).
2. Pass explicit `encoding='utf-8', errors='surrogateescape'` (or decode raw
   bytes with the existing `_auto_decode` UTF-8 → Latin-1 fallback) so output
   is never lost and never raises.
3. Use the same error policy for `input=payload` or encode to bytes first.
4. Catch `UnicodeError` alongside `OSError`/`TimeoutExpired` and report a
   helpful message; add tests for invalid UTF-8 stdout and stderr.
