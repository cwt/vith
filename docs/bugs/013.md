# New buffer inserted before the active buffer while the comment says after

**Category:** correctness (inherited) · **Area:** `vith/window_arrangement.py` · **Found at:** deep review, hg rev 164 (2026-11-06)

## Summary

`_add_editor_buffer` claims to insert the new buffer "right after the
currently active one" but actually inserts **at** the active buffer's own
index, which places the new buffer *before* it in `editor_buffers` — the list
that drives `:buffers` numbering in [`BufferListOverlay`](../../vith/layout.py)
and `:b <n>`.

## Evidence

* [`vith/window_arrangement.py:386-391`](../../vith/window_arrangement.py):
  comment says "Append right after the currently active one" but the code does
  `self.editor_buffers.insert(index, editor_buffer)` where
  `index = self.editor_buffers.index(self.active_editor_buffer)`.
* Consumer: [`vith/window_arrangement.py:517-532`](../../vith/window_arrangement.py)
  (`list_open_buffers` indexes `enumerate(self.editor_buffers)`);
  [`go_to_buffer`](../../vith/window_arrangement.py) `362-372` maps
  `int(buffer_name) == i`.

## Impact

Buffer numbering disagrees with the documented mental model (and with vim's
`:buffers` growth), making `:b 2` slightly surprising after splitting windows.

## Fix direction

Either insert at `index + 1` to match the comment, or update the comment;
behaviour change requires verifying `go_to_next_buffer` chain conventions.
